# 从零基础到前端架构师：系统化成长大纲

> 适用对象：没有编程经验，希望系统成长为高级前端工程师、前端技术负责人，最终具备前端架构师能力的学习者。
>
> 建议周期：全职学习约 24～30 个月，业余学习约 36～48 个月。周期不是硬指标，真正的毕业条件是完成各阶段的能力验收和代表性项目。
>
> 文档定位：这不是一份需要逐条背诵的知识点目录，而是一张长期能力地图。学习者应按照“理解原理—动手实现—项目应用—复盘取舍—形成规范”的闭环推进。

## 第一阶段：建立学习系统与计算机基础

### 模块 1：理解前端行业与成长目标

#### 1.1 前端工程师解决什么问题

前端工程师不只是“写页面的人”。初级阶段的核心产出是正确还原界面和交互；中级阶段需要独立交付业务模块并保证质量；高级阶段要解决复杂状态、性能、稳定性和协作效率问题；技术负责人需要统筹方案、风险、排期与人员；架构师则要面向多个应用和团队设计可演进的技术体系，并对成本、效率、体验和业务结果负责。

##### 1.1.1 需要建立的行业认知

- 区分网站、Web 应用、移动 H5、管理后台、小程序、桌面应用、服务端渲染应用和跨端应用。
- 理解产品、设计、前端、后端、测试、运维、数据、安全等角色的职责边界。
- 理解需求从提出、分析、设计、开发、测试、灰度、上线到运营的完整生命周期。
- 认识业务开发、基础架构、组件平台、低代码、可视化、音视频、性能体验等不同方向。
- 明白框架只是工具，长期竞争力来自计算机基础、抽象能力、工程能力和业务判断。

###### 1.1.1.1 阶段验收

能够用自己的语言解释前端岗位的五个层级；能够描述一个功能从需求到上线的链路；能够为自己的学习建立阶段目标、时间预算、验收方式和作品输出计划，而不是只收藏教程。

#### 1.2 从零开始的学习原则

##### 1.2.1 输入、练习、项目和复盘闭环

每个知识单元至少经历四次加工：第一次通过文档或课程建立概念；第二次脱离示例手写最小实现；第三次放入真实项目解决约束问题；第四次记录错误、边界、替代方案和适用条件。不要连续观看大量课程却不编码，也不要在完全不理解原理时机械复制项目。

###### 1.2.1.1 建议执行规则

- 每天保留可运行代码、学习笔记或问题记录中的至少一种成果。
- 每周完成一次小型整合练习，并写出“做了什么、为何这样做、哪里失败、下次如何改”。
- 每月清理一次知识债务，把零散记录整理为可检索的主题笔记。
- 每个阶段至少完成一个不能照着教程逐行复刻的独立项目。
- 遇到问题先缩小范围、构造最小复现、阅读错误信息，再使用搜索或向他人求助。

### 模块 2：开发环境与工具入门

#### 2.1 操作系统、终端和文件系统

##### 2.1.1 必学内容

- 文件、目录、路径、扩展名、隐藏文件、权限、进程、端口和环境变量。
- 绝对路径与相对路径，当前工作目录与用户目录的区别。
- 常用终端命令：查看目录、创建目录、复制移动、搜索文本、查看进程、终止进程。
- 命令参数、标准输入、标准输出、错误输出、管道和退出码的基本概念。
- 软件安装、版本管理和 PATH 的作用，避免“命令找不到”时盲目重装。

###### 2.1.1.1 实战与验收

只使用终端创建一个项目目录，生成多层文件结构，查找指定文本，启动本地静态服务器并定位占用端口的进程。能够解释执行命令时操作系统如何找到程序，以及错误信息应该从哪里读起。

#### 2.2 编辑器、浏览器开发者工具与 Git

##### 2.2.1 编辑器效率

- 掌握文件搜索、全文搜索、批量替换、多光标、代码格式化、重命名符号和终端集成。
- 理解扩展插件的成本，保持最小而稳定的插件集合。
- 配置统一缩进、换行、编码、保存格式化和基础代码检查。
- 学会用工作区配置共享团队设置，区分个人偏好和项目规范。

##### 2.2.2 浏览器开发者工具

- Elements 面板检查 DOM、样式来源、盒模型、伪类和可访问性树。
- Console 执行表达式、查看日志、断点和调用栈。
- Network 分析请求、响应、缓存、瀑布流、载荷与时序。
- Sources 设置行断点、条件断点、事件断点和观察表达式。
- Performance、Memory、Application 面板的用途和基本使用方式。

##### 2.2.3 Git 最小工作流

- 工作区、暂存区、本地仓库和远程仓库。
- 初始化、提交、查看历史、创建分支、合并分支和解决简单冲突。
- 编写有意义的提交说明，一次提交表达一个完整意图。
- 理解 `.gitignore`，不提交依赖目录、密钥、临时文件和构建产物。
- 认识变基、挑选提交、标签和回滚的用途，但早期不追求复杂命令技巧。

###### 2.2.3.1 阶段项目：个人学习仓库

建立一个长期维护的学习仓库，包含学习日志、代码练习、问题复盘、项目说明和路线看板。使用功能分支完成一次改动，制造并解决一次合并冲突，为阶段成果打标签。验收重点是提交历史清晰、目录可理解、他人能依据 README 运行内容。

### 模块 3：计算机与编程通识

#### 3.1 程序如何运行

##### 3.1.1 核心概念

- CPU、内存、磁盘、网络和输入输出设备的基本职责。
- 程序、进程、线程、调用栈、堆和垃圾回收的直观含义。
- 源代码、编译、解释、运行时、机器码之间的关系。
- 字节、位、二进制、十六进制、字符集、Unicode 和 UTF-8。
- 本地计算与远程计算，客户端与服务端，状态与无状态。

###### 3.1.1.1 验收问题

能够解释为什么关闭程序后普通内存变量会消失，为什么文本会乱码，为什么同一端口通常不能被两个服务同时监听，为什么网络请求比读取内存慢，以及 JavaScript 源码需要运行时才能执行。

#### 3.2 算法、数据结构与复杂度启蒙

##### 3.2.1 入门范围

- 顺序、分支、循环、递归和状态机等程序结构。
- 数组、链表、栈、队列、集合、映射、树、图的用途。
- 查找、排序、遍历、分治、贪心、动态规划的直觉。
- 时间复杂度和空间复杂度，用数量级判断方案是否可扩展。
- 正确性、可读性、性能之间的平衡。

###### 3.2.1.1 练习要求

用 JavaScript 实现栈、队列、去重、二分查找、树的深度优先遍历和广度优先遍历；为每个实现写输入输出示例、边界条件和复杂度说明。此处不以刷题数量为目标，而以形成数据组织和问题拆解意识为目标。

### 模块 4：HTML 与语义化页面

#### 4.1 文档结构和常用元素

##### 4.1.1 HTML 基础

- 文档类型、`html`、`head`、`body` 和元信息。
- 标题、段落、列表、链接、图片、表格、引用和代码元素。
- 块级与行内内容的历史概念，元素嵌套和内容模型。
- URL、相对地址、资源路径、锚点和下载链接。
- HTML 实体、空白折叠、注释和浏览器容错。

##### 4.1.2 表单与用户输入

- `form`、`input`、`select`、`textarea`、`button`、`label` 和 `fieldset`。
- 输入类型、自动完成、占位符、默认值、禁用与只读。
- 原生校验、提交方式、表单编码和文件上传。
- 受控输入与非受控输入的概念，为框架学习做准备。

###### 4.1.2.1 实战：无样式内容网站

制作一个仅使用 HTML 的个人资料与文章网站，包含导航、文章、数据表、联系表单、图片说明和页脚。关闭 CSS 后页面仍应具备清楚的阅读顺序；只使用键盘可以访问所有交互元素；表单标签和错误提示能够被理解。

#### 4.2 语义化、SEO 与可访问性

##### 4.2.1 语义化设计

- 使用 `header`、`nav`、`main`、`article`、`section`、`aside`、`footer` 表达结构。
- 根据内容层级选择标题，不因为视觉大小滥用标题标签。
- 使用按钮触发动作，使用链接完成导航，避免用 `div` 模拟一切。
- 理解 DOM 结构同时服务于浏览器、搜索引擎、辅助技术和自动化测试。

##### 4.2.2 可访问性基础

- 键盘焦点、焦点顺序、跳过导航、可见焦点和焦点陷阱。
- 图片替代文本、表单可访问名称、状态提示和错误关联。
- 色彩对比度、缩放、减少动态效果和触控目标尺寸。
- ARIA 的补充作用，以及“优先使用原生语义元素”的原则。

##### 4.2.3 SEO 基础

- 页面标题、描述、规范地址、结构化标题和可抓取链接。
- 服务端输出、客户端渲染对抓取和首屏内容的影响。
- 站点地图、robots、结构化数据和社交分享元信息。
- 内容质量、性能、移动端体验与搜索表现的关系。

###### 4.2.3.1 架构师视角

在组件库层统一语义和键盘行为，比在每个业务页面临时修补更可靠。后续设计通用组件时，应把可访问性当作接口契约的一部分，包括焦点管理、ARIA 属性、错误信息、国际化文本和自动化检查。

### 模块 5：CSS 样式与布局体系

#### 5.1 选择器、层叠和盒模型

##### 5.1.1 核心知识

- 基础选择器、组合选择器、属性选择器、伪类和伪元素。
- 继承、层叠来源、优先级、源码顺序和 `!important` 的风险。
- 内容盒、边框盒、外边距折叠、行盒和格式化上下文。
- 常见单位：px、%、em、rem、vw、vh、动态视口单位和无单位数值。
- 颜色、背景、边框、阴影、渐变、字体与文本排版。

###### 5.1.1.1 调试要求

面对“样式没有生效”时，按元素是否匹配、属性是否有效、规则是否被覆盖、父级上下文是否改变、浏览器是否支持的顺序排查。能够从开发者工具的计算样式追踪最终值，而不是持续增加选择器优先级。

#### 5.2 布局系统

##### 5.2.1 普通流、定位和浮动

- 普通文档流和块级排版。
- 相对定位、绝对定位、固定定位、粘性定位及其包含块。
- `z-index` 与层叠上下文，定位元素为何有时无法覆盖。
- 浮动的历史用途及在图文环绕中的合理应用。

##### 5.2.2 Flexbox

- 主轴、交叉轴、伸缩基准、增长、收缩、换行和对齐。
- 单行导航、工具栏、卡片列表、居中、等高栏等典型场景。
- 内容最小尺寸导致溢出的原因，`min-width: 0` 等常见处理。

##### 5.2.3 Grid

- 显式网格、隐式网格、轨道、网格线、区域和间距。
- `fr`、`minmax()`、`repeat()`、自动填充和自动适配。
- 二维页面骨架、仪表盘、图库和复杂卡片排版。

###### 5.2.3.1 实战：三套响应式布局

分别实现博客、商品列表和数据看板。每个页面至少覆盖手机、平板、桌面三档视口，处理长文本、缺失图片、超大数字、空状态和右到左文本等边界。禁止通过大量绝对定位硬编码还原主要布局。

#### 5.3 响应式设计与现代 CSS

##### 5.3.1 响应式策略

- 移动优先与桌面优先的选择依据。
- 媒体查询、容器查询、特性查询和用户偏好查询。
- 流式排版、弹性图片、断点设计和内容驱动布局。
- 高分屏图片、响应式图片、对象适配与图片裁切。

##### 5.3.2 可维护的样式组织

- BEM、工具类、CSS Modules、CSS-in-JS、原子化 CSS 的思想与权衡。
- CSS 自定义属性、设计令牌、主题切换和局部变量。
- 层叠层、低优先级选择器、作用域和组件边界。
- 重置样式、基础样式、组件样式、布局样式和工具样式分层。

##### 5.3.3 动画与交互反馈

- transition、transform、animation 和关键帧。
- 合成属性与重排重绘，避免高成本动画。
- 入场、退场、状态切换、骨架屏和微交互的节奏。
- 尊重 `prefers-reduced-motion`，动画不能阻碍任务完成。

###### 5.3.3.1 阶段项目：响应式内容平台

独立完成一个多页面内容平台，至少包含首页、列表、详情、搜索、登录表单和个人中心。建立颜色、字号、间距、圆角、阴影等令牌；支持亮暗主题；通过键盘导航；在 320px 到宽屏范围内无明显横向溢出。为 CSS 结构、断点策略和组件复用写一份设计说明。

### 模块 6：视觉还原和设计协作

#### 6.1 基础视觉素养

##### 6.1.1 学习内容

- 对齐、亲密性、重复、对比和留白等基本设计原则。
- 字体家族、字重、字号、行高、字距与阅读节奏。
- 主色、中性色、语义色、状态色与对比度。
- 网格、节奏、密度、视觉层级和信息分组。
- 常见图片格式、矢量与位图、压缩、透明度和色彩空间。

###### 6.1.1.1 验收方式

从设计稿提炼出设计令牌和组件清单，而不是逐页面抄数值；对比实现与设计稿，能够分类说明结构偏差、字体偏差、间距偏差、色彩偏差和交互状态缺失；能够与设计师讨论可实现性和一致性。

## 第三阶段：JavaScript 编程基础

### 模块 7：语言语法与程序控制

#### 7.1 值、类型、变量和表达式

##### 7.1.1 基础知识

- `number`、`string`、`boolean`、`null`、`undefined`、`symbol`、`bigint`。
- 对象与原始值的区别，值传递、引用共享和可变性。
- `let`、`const`、`var` 的作用域和使用原则。
- 算术、比较、逻辑、赋值、空值合并和可选链运算符。
- 显式类型转换与隐式类型转换，严格相等的默认选择。
- 模板字符串、数字精度、NaN 和浮点数陷阱。

###### 7.1.1.1 练习标准

实现价格计算、温度换算、字符串模板、输入校验和配置合并等小函数。每个函数说明参数、返回值、非法输入和边界值；能够使用控制台验证猜想，而不是依赖直觉判断类型转换结果。

#### 7.2 分支、循环和函数

##### 7.2.1 控制结构

- `if`、`switch`、条件表达式和短路求值。
- `for`、`while`、`for...of` 与数组迭代方法。
- `break`、`continue`、提前返回和减少嵌套。
- 函数声明、函数表达式、箭头函数、参数、默认值和剩余参数。
- 纯函数、副作用、输入输出契约和单一职责。

###### 7.2.1.1 实战：命令行记账核心

先不制作界面，使用函数实现新增记录、分类、筛选、汇总、预算提醒和导出文本。要求将数据处理与输入输出分离，处理空集合、负数、无效日期和重复记录，并为关键函数编写简单断言。

### 模块 8：集合、对象与常用内置能力

#### 8.1 数组与对象

##### 8.1.1 数组操作

- 创建、访问、增删、复制、拼接、切片和排序。
- `map`、`filter`、`reduce`、`find`、`some`、`every` 的语义。
- 原地修改与返回新数组的区别，排序比较函数的必要性。
- 多维数组、扁平化、分组、索引和集合运算。

##### 8.1.2 对象操作

- 属性访问、计算属性、遍历、解构、展开和浅拷贝。
- 属性描述符、可枚举性、原型继承的初步概念。
- `Map`、`Set`、`WeakMap`、`WeakSet` 的适用场景。

###### 8.1.2.1 数据建模练习

### 模块 26：测试思想与测试分层

#### 26.1 为什么测试以及测试什么

##### 26.1.1 测试基本原则

- 测试保护可观察行为，不与内部实现过度绑定。

### 模块 27：单元、组件与集成测试

#### 27.1 单元测试

##### 27.1.1 必学内容

- 测试替身：stub、spy、mock、fake 的目的。
- 时间、随机数、网络、存储等不确定依赖的隔离。
- 边界值、等价类、状态转换和属性测试思想。
- 可测试设计与依赖注入，避免为测试暴露内部细节。

#### 27.2 组件和集成测试

##### 27.2.1 用户视角测试

- 模拟真实点击、输入、键盘和焦点行为。

- 使用网络模拟层替代直接 mock 请求函数，提升集成价值。
- 谨慎使用快照，避免大量无人审阅的更新。

###### 27.2.1.1 验收任务

为中型业务应用补充核心领域函数、复杂表单、权限路由、请求失败和乐观更新测试。故意引入五类缺陷验证测试能否捕获；记录漏检原因，并优化测试设计而不是只增加断言数量。

#### 28.1 端到端测试

##### 28.2.1 补充质量门

#### 29.1 评审方法

##### 29.1.1 评审维度

### 模块 30：性能指标与测量体系

#### 30.1 用户体验指标

##### 30.1.1 指标体系

### 模块 31：加载与运行时性能

#### 31.1 加载优化

##### 31.1.1 优化手段

- 减少关键资源体积和请求链，压缩、分包、按需加载。
- preload、prefetch、preconnect 的准确用途和优先级风险。
- 图片尺寸、格式、响应式加载、懒加载和解码。
- 字体子集、加载策略、回退字体和布局偏移。
- SSR、SSG、流式渲染、边缘渲染的体验与运维取舍。

#### 31.2 运行时优化

##### 31.2.1 优化手段

- 识别长任务，拆分任务、延后非关键任务和 Worker 并行。
- 避免布局抖动，批量读取写入，使用合成友好动画。
- 框架渲染分析、状态订阅范围、稳定输入和记忆化。
- 虚拟列表、大表格、分片渲染和增量计算。
- 缓存计算结果，同时控制失效、内存和一致性成本。

###### 31.2.1.1 性能专项

选择一个真实页面完成“测量—定位—假设—实验—验证—监控”闭环。至少优化一项加载指标和一项交互指标，保存火焰图或瀑布证据。报告必须包含没有采用的方案及原因，防止优化变成不可维护的技巧集合。

### 模块 32：前端监控与故障治理

#### 32.1 可观测数据

##### 32.1.1 监控体系

- JavaScript 异常、Promise 拒绝、资源错误和请求错误。
- source map 还原、堆栈聚合、指纹和版本关联。
- 性能指标、用户行为轨迹、关键业务事件和自定义日志。
- Trace ID 串联浏览器、网关和服务端调用。
- 采样、脱敏、数据保留、成本与隐私合规。

#### 32.2 告警与事故处理

##### 32.2.1 稳定性机制

- 服务等级指标、服务等级目标和错误预算的基本思想。
- 告警阈值、突增检测、降噪、聚合和升级路径。
- 熔断、降级、重试、限流、兜底页和远程开关。
- 事故发现、止血、定位、恢复、沟通和复盘。
- 无责复盘关注系统改进，不把根因简单归结为个人失误。

###### 32.2.1.1 演练任务

模拟发布后白屏、接口错误率上升、静态资源加载失败和第三方脚本阻塞。要求监控能在用户集中投诉前发现问题，值班人员能按手册定位版本和影响范围，使用开关或回滚恢复，并完成时间线与改进项明确的复盘。

- 数据库、缓存、消息队列的基本职责和使用边界。

###### 33.2.1.1 安全要求

密码只保存经过合适算法处理的哈希；所有外部输入都做运行时校验；数据库操作使用参数化方式；鉴权与授权分离；日志不记录密码、完整令牌和敏感个人信息；为接口设置大小、速率和超时限制。

### 模块 34：BFF、SSR 与全栈框架

#### 34.1 BFF 架构

##### 34.1.1 BFF 职责

- 面向特定前端聚合后端接口、裁剪数据和适配协议。
- 统一会话、权限上下文、错误格式和服务发现。
- 处理跨服务编排，但避免复制核心业务规则成为新单体。
- 超时预算、并发聚合、部分失败、缓存和降级。
- 与网关、通用 API 服务、微服务的边界。

#### 34.2 SSR 和全栈渲染

##### 34.2.1 渲染模式

- CSR、SSR、SSG、增量生成、流式渲染和局部水合。
- 首屏、SEO、个性化、缓存、服务器成本和开发复杂度。
- 水合不一致、服务端数据预取和客户端接管。
- 服务端组件与客户端组件边界，序列化和依赖限制。
- 边缘运行时的延迟优势与 API、调试、成本限制。

###### 34.2.1.1 阶段项目：同构内容与交易应用

构建一个包含公开内容页和登录后交易页的全栈应用。公开页使用适合搜索和缓存的渲染方式，交易页处理会话、权限与实时状态。实现 BFF 聚合、统一追踪、缓存失效、错误降级和安全头，并用架构决策记录说明为何不同页面采用不同渲染模式。

### 模块 35：后端协作与分布式系统常识

#### 35.1 前端必须理解的分布式问题

##### 35.1.1 核心常识

- 网络可能延迟、丢包、重复和乱序，远程调用不会像本地函数一样可靠。
- 超时与重试必须配合幂等性，盲目重试会放大故障。
- 最终一致性、读写延迟和用户可见的中间状态。
- 分布式事务的困难，补偿、对账和状态机。
- 服务版本并存，接口变更需要兼容窗口。

###### 35.1.1.1 协作验收

与后端共同定义订单提交协议：请求唯一键、状态机、重复提交、超时查询、失败重试、取消和对账。能够把“按钮点了没反应”拆成前端状态、网络、网关、服务、数据库和消息等可能环节，并用 Trace ID 沟通证据。

## 第十一阶段：组件库、设计系统与体验标准

### 模块 36：可复用组件设计

#### 36.1 组件 API 与边界

##### 36.1.1 设计原则

- 从稳定语义和真实复用场景出发，不从重复几行 JSX 出发。
- 属性保持正交，受控与非受控行为明确，默认值可预测。
- 组合、插槽、渲染函数、上下文和命令式句柄的取舍。
- 样式覆盖、尺寸、状态、主题和国际化扩展点。
- 避免布尔属性爆炸和一个组件承担互斥场景。

###### 36.1.1.1 组件验收矩阵

每个基础组件至少检查默认、悬停、聚焦、激活、禁用、加载、错误、只读、长文本、空内容、键盘、触屏、亮暗主题和多语言。API 文档需要给出正确用法、错误用法、可访问性说明和版本变化。

### 模块 37：设计系统工程

#### 37.1 从令牌到组件

##### 37.1.1 系统分层

- 原始令牌、语义令牌、组件令牌和主题覆盖。
- 字体、颜色、间距、圆角、阴影、动效和层级规范。
- 基础元素、复合组件、业务模式和页面模板。
- 设计工具变量与代码令牌同步，避免双重真相来源。
- 文档站、组件沙箱、交互示例和设计使用指南。

#### 37.2 发布与采用治理

##### 37.2.1 长期维护

- 语义化版本、变更日志、弃用警告和迁移脚本。
- 多框架支持的成本，核心逻辑与框架适配层分离。
- 组件使用率、重复实现率、缺陷率和升级覆盖率。
- 需求受理、设计评审、贡献流程和所有者机制。
- 允许业务逃生，但要求例外可追踪并反馈系统能力。

###### 37.2.1.1 阶段项目：企业设计系统

完成不少于十五个基础组件、五个复合模式和一套令牌，支持亮暗主题、中文英文、键盘操作和视觉回归。发布到内部包工作区，提供交互文档、升级策略和贡献指南，并选择两个应用验证真实采用而非只展示 Demo。

### 模块 38：国际化、可访问性与体验治理

#### 38.1 国际化工程

##### 38.1.1 学习内容

- 文案抽取、消息 ID、变量、复数、性别和富文本翻译。
- 日期、数字、货币、单位、姓名和地址格式。
- 文本膨胀、字体覆盖、右到左布局和镜像资源。
- 语言检测、路由、回退、按需加载和翻译版本。
- 伪本地化、缺失翻译监控和翻译平台协作。

#### 38.2 可访问性治理

##### 38.2.1 组织能力

- 建立组件级自动检查、页面扫描和人工键盘巡检。
- 屏幕阅读器测试关键任务流，而非只检查属性。
- 将可访问性纳入设计验收、代码评审和发布门禁。
- 对问题分级，设定修复时限和豁免记录。
- 通过设计系统消除重复问题，培训团队形成共同语言。

###### 38.2.1.1 验收项目

选取登录、搜索、创建订单三条旅程，完成键盘、屏幕阅读器、200% 缩放、颜色对比和减少动画测试。输出问题清单、严重级别、组件级根因和治理计划，修复后通过自动与人工双重回归。

## 第十二阶段：架构模式、微前端与跨端体系

### 模块 39：前端应用架构

#### 39.1 分层、模块化与依赖规则

##### 39.1.1 常见架构思想

- 按技术层、按业务功能、按领域切片的目录组织。
- 展示、应用流程、领域逻辑和基础设施的职责划分。
- 依赖倒置、端口适配器、整洁架构在前端的适度应用。
- 模块公开接口、内部实现、跨模块通信和循环依赖治理。
- 架构适应变化，不为了形式强迫简单页面套复杂层级。

###### 39.1.1.1 架构评审任务

对一个不断增长的后台系统绘制现状依赖图，找出共享目录膨胀、跨模块状态、隐式副作用、重复请求和循环依赖。提出分阶段重构方案，每一步都可独立发布、验证收益并可回退。

#### 39.2 状态与流程架构

##### 39.2.1 复杂状态设计

- 实体状态、视图状态、会话状态和工作流状态分离。
- 有限状态机、状态图、事件和守卫条件。
- 事件驱动、命令处理、审计日志和可撤销操作。
- 多标签页、实时协作、离线同步和冲突解决。
- 不把状态库当作流程模型，先明确业务状态转换。

###### 39.2.1.1 实战：订单工作台状态机

为草稿、待审核、已批准、处理中、已完成、已取消的订单建立状态机，处理角色权限、超时、撤回、并发编辑和服务端拒绝。界面只能根据合法状态提供操作，所有转换可追踪并可测试。

### 模块 40：微前端与多团队协作

#### 40.1 是否需要微前端

##### 40.1.1 决策维度

- 组织是否存在独立团队、独立节奏和明确业务边界。
- 单体应用的真实痛点是代码耦合、构建慢还是协作流程。
- 路由级集成、运行时容器、模块联邦、Web Components 等方式。
- 依赖共享、样式隔离、运行时隔离和通信协议。
- 首屏性能、调试、测试、监控、版本和故障扩散成本。

#### 40.2 微前端治理

##### 40.2.1 平台契约

- 主应用与子应用生命周期、路由、鉴权和上下文协议。
- 全局事件、共享状态和跨应用跳转的最小公共面。
- 依赖版本、组件规范、样式命名和浏览器兼容基线。
- 独立发布、灰度、回滚、监控归属和故障隔离。
- 本地联调、集成环境和端到端测试策略。

###### 40.2.1.1 决策记录

分别为三种场景写决策：单团队中型应用、多个团队共享后台、强隔离第三方模块。至少一个场景应明确拒绝微前端，并用模块化单体或包级边界解决。架构能力体现在选择合适复杂度，而不是采用最复杂方案。

### 模块 41：跨端与桌面应用

#### 41.1 移动跨端

##### 41.1.1 学习范围

- 响应式 Web、PWA、WebView 混合应用和跨端框架的差异。
- 小程序运行环境、双线程或桥接通信的基本概念。
- React Native、Flutter 等方案的渲染模型概览。
- 原生能力桥接、权限、包体、热更新和审核约束。
- 触屏交互、弱网、后台切换、设备碎片化和性能预算。

#### 41.2 桌面端

##### 41.2.1 学习范围

- Electron 主进程、渲染进程、预加载脚本和进程通信。
- 上下文隔离、Node 集成关闭和最小权限暴露。
- 窗口、菜单、托盘、文件系统和自动更新。
- 包体、内存、启动速度、签名与多平台分发。
- Tauri 等轻量方案的边界与团队语言成本。

###### 41.2.1.1 选型项目

为一个需要离线文件处理、系统通知和多窗口的产品完成 Web、PWA、Electron、原生跨端四种方案评估。用用户体验、能力覆盖、性能、安全、团队技能、交付周期和长期维护成本建立加权决策表，再制作最小技术验证。

- 把节省的时间投入更高价值的设计与验证，而不是扩大无审查产出。

###### 44.2.1.1 架构师任务

为团队制定 AI 辅助开发指南，选择三个高频场景做小规模试点，以交付周期、缺陷率、评审负担和开发者体验评估收益。明确禁止场景、人工责任、数据策略和退出机制，避免把工具热度直接等同于组织生产力。

## 第十四阶段：业务建模、复杂系统与架构治理

### 模块 45：领域理解与业务建模

#### 45.1 从需求到模型

##### 45.1.1 建模方法

- 识别参与者、目标、规则、实体、值对象、事件和约束。
- 统一术语，避免产品、前端、后端对同一概念含义不同。
- 用户旅程、用例、流程图、状态机和领域事件。
- 核心域、支撑域、通用域和限界上下文的基本思想。
- 前端视图模型与后端领域模型不必机械一致。

###### 45.1.1.1 建模工作坊

选择电商售后、在线审批或订阅计费，组织一次事件梳理。输出术语表、上下文边界、核心流程、异常流程、状态机和接口草案。邀请产品、后端、测试共同评审，以发现隐藏规则，而不是由前端单方面创造业务事实。

### 模块 46：复杂业务前端

#### 46.1 权限、流程与配置化

##### 46.1.1 权限体系

- 身份、角色、权限、资源、动作、数据范围和策略。
- 菜单权限、路由权限、按钮权限与服务端授权。
- RBAC、ABAC 的适用差异，权限缓存和变更生效。
- 前端隐藏不等于安全，服务端必须执行最终检查。
- 权限矩阵、审计日志和越权测试。

##### 46.1.2 流程与规则

- 审批节点、条件分支、并行会签、撤回、转交和超时。
- 规则配置、表达式、版本、发布、回滚和模拟运行。
- 配置驱动 UI 的 Schema、组件注册、校验和安全边界。
- 低代码的适用范围：高重复、规则稳定、可组合场景。
- 防止无限配置化把代码问题变成更难调试的元数据问题。

###### 46.1.2.1 复杂项目

实现一个可配置审批工作台：设计流程、发布版本、创建申请、任务处理、权限控制、审计追踪和数据看板。前端需要处理草稿恢复、表单 Schema、流程可视化、多人操作冲突和旧版本兼容。输出业务模型与技术模型的映射文档。

### 模块 47：架构决策与演进

#### 47.1 架构设计方法

##### 47.1.1 先约束后方案

- 明确业务目标、用户规模、团队结构、时间预算和合规要求。
- 识别功能需求与质量属性：性能、稳定、安全、可维护、可扩展。
- 找出风险最高、最不确定和最难回退的决策。
- 通过技术验证、压测或原型降低不确定性。
- 使用多个候选方案比较，而不是先选技术再补理由。

##### 47.1.2 架构决策记录

- 背景与问题、决策驱动因素、候选方案和最终选择。
- 正面影响、负面影响、风险、验证和回顾日期。
- 决策状态：提出、接受、弃用、被替代。
- 记录“为什么”，代码和配置负责表达“是什么”。
- 架构文档随系统演进，过期文档要更新或明确归档。

###### 47.1.2.1 评审验收

完成至少五份决策记录，主题可覆盖框架、渲染方式、状态方案、Monorepo、微前端、组件库或监控。每份都要有可验证驱动因素和明确代价。六个月后回顾假设是否成立，形成决策反馈闭环。

#### 47.2 遗留系统治理

##### 47.2.1 渐进演进

- 先建立可观测基线和测试保护，再进行高风险重构。
- 绞杀者模式、适配层、双写、流量切换和功能开关。
- 技术债分类：阻碍交付、质量风险、效率损耗和认知负担。
- 用利息、影响范围和修复成本排序，不追求一次性重写。
- 重写必须有业务价值、迁移路径、并行成本和退出标准。

###### 47.2.1.1 迁移计划

为一个假设的旧框架大型系统制定十二个月迁移路线：资产盘点、指标基线、边界切分、公共能力兼容、首个试点、规模迁移和旧系统下线。明确每阶段用户影响、双轨成本、完成定义和停止条件。

### 模块 48：成本、合规与可持续架构

#### 48.1 成本意识

##### 48.1.1 总拥有成本

- 开发时间只是成本的一部分，还包括构建、托管、流量、监控和支持。
- 第三方服务按请求、用户、事件或流量计费的增长曲线。
- 自研与采购比较：能力匹配、集成、迁移、锁定和运维。
- 性能优化与成本优化可能一致，也可能引入额外复杂度。
- 使用量仪表盘、预算告警和容量预测。

#### 48.2 隐私、合规与绿色实践

##### 48.2.1 架构责任

- 数据最小化、目的限制、授权、删除和保留周期。
- Cookie 同意、埋点分类、个人信息脱敏和访问审计。
- 开源许可证、第三方字体图片和代码来源治理。
- 减少不必要资源、计算和轮询，同时改善性能与能耗。
- 具体法规随地区和时间变化，项目必须与法务安全团队确认。

###### 48.2.1.1 验收任务

为业务应用建立前端数据清单：采集项、用途、来源、去向、保留时间、用户控制和责任人。再制作第三方脚本清单与风险等级，设计在脚本不可用或不同意采集时仍可完成核心任务的降级路径。

## 第十五阶段：技术领导力与架构师软技能

### 模块 49：沟通、协作和影响力

#### 49.1 技术沟通

##### 49.1.1 表达能力

- 先对齐问题、目标和约束，再展示技术细节。
- 面向管理者讲价值、风险和选择，面向工程师讲契约与实现。
- 用图、示例、数据和原型降低抽象方案的理解成本。
- 区分事实、推断、假设和偏好，明确不确定性。
- 会议有议题、决策、责任人和截止时间，文档保留上下文。

###### 49.1.1.1 练习方式

将同一架构方案分别写成三分钟管理层摘要、十五分钟团队分享和详细技术设计。邀请不同角色复述理解，若关键结论不一致，优化表达而不是归咎听众。

#### 49.2 跨团队推动

##### 49.2.1 影响力来源

- 通过共同目标、可靠数据和小规模成功建立信任。
- 识别利益相关者、决策权、使用者和潜在阻力。
- 为迁移提供工具、文档、支持和收益，而非只发布强制规则。
- 允许团队在护栏内自治，例外通过透明机制管理。
- 对公共项目建立路线图、反馈渠道和服务承诺。

###### 49.2.1.1 推广任务

模拟推动统一请求 SDK 或组件库：调查现状、量化重复成本、选择试点、制定兼容方案、收集反馈、逐步推广并衡量采用率。若方案实际增加负担，应调整或撤回，而不是为了证明架构正确强行推广。

### 模块 50：技术规划与项目领导

#### 50.1 路线图和优先级

##### 50.1.1 规划方法

- 从业务目标和工程痛点生成候选项目。
- 用影响、紧迫性、风险、工作量和依赖排序。
- 区分必须做、应该做、可选和明确不做。
- 给探索任务设置时间盒，用验证结果决定继续投入。
- 路线图表达方向和结果，不承诺无法控制的远期精确日期。

#### 50.2 交付管理

##### 50.2.1 执行能力

- 拆分里程碑、识别关键路径、外部依赖和集成风险。
- 估算包含不确定性，不把单点数字当成保证。
- 风险登记、预警、备选方案和范围管理。
- 决策日志、进度透明、质量门和发布准备。
- 项目结束衡量结果与维护成本，而不是只宣布按时上线。

###### 50.2.1.1 架构项目计划

为“统一前端工程平台”编写半年路线图，覆盖调研、试点、核心能力、迁移和运营。定义成功指标，例如环境搭建时间、构建时长、缺陷逃逸、依赖升级覆盖和开发满意度；同时声明不会解决的问题，控制平台边界。

### 模块 51：人才培养与团队机制

#### 51.1 能力模型和指导

##### 51.1.1 人才发展

- 用可观察行为描述职级，不用“影响力强”等模糊词单独评估。
- 为成员匹配略高于当前能力且有支持的任务。
- 反馈针对行为、影响和改进建议，及时且具体。
- 通过结对、设计评审、代码评审和复盘传递思考方式。
- 建立专家路线与管理路线，避免晋升只有转管理一条路。

#### 51.2 健康工程文化

##### 51.2.1 团队机制

- 心理安全允许暴露风险、承认未知和报告事故。
- 质量是团队系统结果，不依赖少数“救火英雄”。
- 控制会议、打断和值班负担，保护深度工作时间。
- 文档、轮岗和备份所有者降低关键人风险。
- 关注交付、质量、学习和可持续性之间的平衡。

###### 51.2.1.1 验收标准

设计一套从初级到架构师的前端能力矩阵，为每一级提供行为例证和晋级证据。选择一名假设成员制定三个月成长计划，包括目标任务、支持方式、检查节点和风险，而不是简单列出需要学习的技术名词。

### 模块 52：架构师的判断与职业伦理

#### 52.1 在不确定中决策

##### 52.1.1 判断框架

- 区分可逆和不可逆决策，可逆决策快速试验。
- 优先处理高影响、高不确定和高耦合问题。
- 承认信息不足，通过实验、监控和阶段回顾修正。
- 避免沉没成本、从众、权威和新技术偏见。
- 对结果负责，但不伪装确定性或隐瞒坏消息。

###### 52.1.1.1 职业底线

架构师不应为了指标操纵用户、默认过度采集、隐藏重大风险或使用未经授权的资产；不能以进度为由绕过已知严重安全问题；在商业目标与用户权益冲突时，应清楚记录风险并推动合适的决策层参与。

## 第十六阶段：综合项目、能力认证与持续成长

### 模块 53：毕业级综合项目

#### 53.1 项目一：多应用企业协作平台

##### 53.1.1 功能范围

- 组织、成员、角色、项目、任务、评论、文件、通知和审计。
- 公开分享页、登录工作台、管理后台和移动适配。
- 复杂筛选、实时更新、离线草稿、批量操作和数据看板。
- 中英文、亮暗主题、键盘操作和关键流程可访问性。
- 权限矩阵、数据范围、操作确认和恢复机制。

##### 53.1.2 架构范围

- Monorepo 管理多个应用、组件、SDK、配置和工具包。
- 至少两种渲染策略，明确选择依据和缓存方式。
- BFF 聚合、接口契约、统一错误、追踪和安全边界。
- 测试分层、性能预算、监控告警、灰度和回滚。
- 设计系统、工程文档、决策记录和贡献流程。

###### 53.1.2.1 毕业验收

项目必须可部署、可观察、可回滚、可由他人接手。除代码外，应包含需求边界、领域模型、上下文图、容器图、关键序列图、数据流、威胁模型、性能报告、测试策略、运行手册、故障复盘和不少于五份架构决策记录。

#### 53.2 项目二：前端研发效能平台

##### 53.2.1 平台范围

- 项目创建、模板管理、依赖健康、构建分析和质量看板。
- CI 任务编排、预览环境、发布审批、灰度和回滚入口。
- 组件目录、文档搜索、变更日志和迁移提示。
- 错误、性能和版本数据关联，支持从告警定位到提交。
- 权限、审计、指标采集和多团队隔离。

###### 53.2.1.1 价值验收

平台项目不能只验收功能数量。必须选择至少三个基线指标，例如新项目启动时间、构建中位时长、重复配置数量、发布失败率或故障定位时间，用试点前后数据验证价值；同时核算平台维护成本和团队采用阻力。

### 模块 54：架构师能力答辩

#### 54.1 技术深度证据

##### 54.1.1 答辩主题

- 解释浏览器渲染、事件循环、模块加载和框架更新机制。
- 从真实性能记录定位瓶颈并提出可验证优化。
- 诊断内存泄漏、白屏、请求竞态和发布不一致。
- 分析构建依赖图、缓存和代码分割策略。
- 对安全威胁给出分层防护，而非背诵攻击名称。

#### 54.2 架构广度证据

##### 54.2.1 答辩主题

- 在 CSR、SSR、SSG 等渲染模式间做有约束的选择。
- 在单体、模块化单体、Monorepo、微前端间选择组织方式。
- 设计组件系统、状态体系、权限体系、监控和发布平台。
- 处理兼容、迁移、成本、合规、团队技能和供应商锁定。
- 说明方案适用边界、失败模式、回滚和演进路径。

#### 54.3 领导力证据

##### 54.3.1 答辩主题

- 推动跨团队方案从调研、试点到规模采用。
- 主导事故处理和无责复盘，形成系统改进。
- 培养成员、建立机制、平衡短期交付和长期治理。
- 以业务和用户结果解释技术投入。
- 面对反对意见能澄清事实、调整方案并记录决策。

###### 54.3.1.1 认证方式

建议由前端、后端、测试、产品和管理者共同参与答辩。候选人提交项目材料，进行架构陈述、故障推演、需求变更和方案质询。评价重点是证据、思考过程、边界意识和修正能力，不以是否说出某个标准答案为准。

### 模块 55：分阶段时间表与里程碑

#### 55.1 零基础到初级前端：第 1～6 个月

##### 55.1.1 主要里程碑

- 掌握 HTML、CSS、JavaScript 基础和 Git 工作流。
- 能独立实现响应式页面和原生 JavaScript 应用。
- 能对接接口、处理表单、错误和本地存储。
- 完成两个可部署项目并写清运行说明。
- 开始形成调试流程，而不是遇错就重写。

###### 55.1.1.1 晋级条件

在不给出逐步教程的情况下，根据设计稿和接口文档独立完成一个小型应用；代码结构清楚；兼顾基本响应式、语义、异常状态和安全输入；能够通过开发者工具定位常见布局、脚本和网络问题。

#### 55.2 初级到中级前端：第 7～12 个月

##### 55.2.1 主要里程碑

- 精通一个主流框架，掌握 TypeScript、路由、状态和请求。
- 理解浏览器、HTTP、异步和模块化原理。
- 能独立负责中型业务模块，完成测试和发布。
- 具备基础性能、安全和可访问性意识。
- 能进行清楚的代码评审和方案说明。

###### 55.2.1.1 晋级条件

独立交付跨多个页面的业务功能，对需求边界、状态设计、接口联调、测试、监控和上线负责；线上出现问题时能收集证据、快速止血和定位，不把所有问题直接转交他人。

#### 55.3 中级到高级前端：第 13～20 个月

##### 55.3.1 主要里程碑

- 掌握工程化、测试体系、性能和稳定性治理。
- 能设计组件库、复杂状态和模块边界。
- 熟悉 Node.js、BFF、SSR 与发布策略。
- 负责跨模块项目并指导其他成员。
- 用指标证明优化效果，能够渐进治理遗留系统。

###### 55.3.1.1 晋级条件

主导一个高复杂或跨团队项目，在设计阶段识别主要风险，建立清晰契约与质量门，按阶段交付并处理变化；项目上线后在性能、质量或效率上获得可验证改进，同时没有留下不可解释的复杂度。

#### 55.4 高级前端到技术负责人：第 21～28 个月

##### 55.4.1 主要里程碑

- 负责一个应用或业务域的技术方向和交付质量。
- 建立工程规范、监控、发布和故障处理机制。
- 跨角色拆解需求、管理依赖、风险和路线图。
- 推动公共能力，关注采用率和维护成本。
- 培养成员、主持设计评审和事故复盘。

###### 55.4.1.1 晋级条件

团队在其不直接编写所有代码的情况下仍能稳定交付；关键决策有记录，系统风险可观察，故障可恢复，成员能力在增长。技术负责人不是最忙的救火者，而是让团队不依赖救火也能工作的机制建设者。

#### 55.5 技术负责人到前端架构师：第 29 个月以后

##### 55.5.1 主要里程碑

- 负责多个应用或团队之间的技术一致性和演进方向。
- 建立架构原则、决策机制、平台能力和治理指标。
- 平衡业务速度、用户体验、稳定、安全、成本和人才结构。
- 主导不可逆或高风险决策，并为迁移和退出负责。
- 在组织内形成可复用的架构知识和技术领导力。

###### 55.5.1.1 架构师达标定义

能够在不确定、资源有限、多人协作和遗留约束下，把复杂问题转化为清晰边界、合理方案和可执行演进路径；能解释取舍、验证结果、承认错误并调整；其价值体现在系统与团队长期变得更容易改变，而不是产出更多架构图。

### 模块 56：每周、每月与每季度执行模板

#### 56.1 每周学习循环

##### 56.1.1 推荐节奏

- 约 30% 时间阅读官方文档、规范、优秀源码和技术文章。
- 约 50% 时间编码、调试、测试和完成项目。
- 约 20% 时间复盘、整理笔记、评审和讲解输出。
- 每周选择一个主问题，避免同时切换太多主题。
- 留出缓冲处理卡点，不用牺牲睡眠维持计划表。

###### 56.1.1.1 周复盘问题

本周解决了什么真实问题？哪些知识能脱离资料复现？最大的错误假设是什么？项目中新增了什么技术债？有什么证据证明能力提升？下周最重要的一件事是什么？哪些内容决定暂时不学？

#### 56.2 月度和季度检查

##### 56.2.1 月度检查

- 完成一个可展示、可运行、可解释的增量。
- 回看错误记录，找出重复发生的调试盲点。
- 清理依赖、无效分支、过期笔记和未完成实验。
- 邀请他人做一次代码或方案评审。
- 根据实际投入调整下月范围，而不是累积延期任务。

##### 56.2.2 季度检查

- 对照能力矩阵评估技术深度、工程能力、业务理解和协作。
- 选择一项短板做专项，选择一项优势形成公开作品。
- 更新作品集、架构决策、性能报告和事故复盘。
- 检查所学是否仍服务于目标岗位和业务方向。
- 为下一季度设定结果型目标与明确不做清单。

###### 56.2.2.1 防止虚假进步

不要用看完课程数、收藏文章数、提交次数和框架数量单独衡量成长。更可靠的证据是：能否独立完成、能否解释原理、能否处理边界、能否用数据验证、能否让他人接手、能否在约束变化时调整方案。

### 模块 57：知识来源与持续学习

#### 57.1 信息来源优先级

##### 57.1.1 建议顺序

- Web 标准、语言规范、框架和工具的官方文档。
- 浏览器厂商、核心维护者和高质量工程团队的技术资料。
- 经过同行评审的书籍、课程和公开案例。
- 源码、问题跟踪、变更记录和真实性能数据。
- 社区文章与短视频用于发现线索，重要结论返回一手资料验证。

#### 57.2 建立个人知识系统

##### 57.2.1 组织方式

- 概念笔记解释“是什么、为何、边界和关联”。
- 操作手册记录可重复执行的诊断与发布步骤。
- 决策记录保存上下文和取舍。
- 错误案例保留现象、根因、证据和预防措施。
- 项目索引把代码、文档、指标和复盘连接起来。

###### 57.2.1.1 最终原则

前端技术会持续变化，架构师不能依赖固定工具清单获得长期安全感。应保持对浏览器平台、语言生态、业务变化和组织能力的观察，用小实验验证新技术，用明确退出标准控制尝试成本，把稳定原理与变化工具分开管理。

- 能设计合理的测试分层并处理偶发测试。
- 能建立性能预算、错误监控、告警和回滚机制。
- 能在事故中止血、定位、沟通和复盘。

###### A.2.1.1.1 通过证据

一个有完整流水线的项目；一份测试策略；一份性能专项报告；一次发布演练和一次事故复盘；能够展示指标改进而非只展示配置文件。

### A.3 架构与业务能力

#### A.3.1 系统设计

##### A.3.1.1 检查项

- 能从业务目标、领域规则和质量属性推导架构。
- 能划分模块、状态、接口、信任边界和团队责任。
- 能在多种渲染、仓库、集成和跨端方案间取舍。
- 能设计渐进迁移路径，处理兼容、成本和遗留约束。
- 能通过决策记录和图示让方案可评审、可演进。

###### A.3.1.1.1 通过证据

一个毕业级综合项目；一套领域与架构文档；至少五份经过回顾的架构决策；一份遗留系统迁移计划；一次面对需求变化的方案修订记录。

### A.4 领导力与组织能力

#### A.4.1 团队影响

##### A.4.1.1 检查项

- 能面向不同角色准确沟通技术价值与风险。
- 能推动跨团队公共方案并根据反馈调整。
- 能规划路线、管理依赖、控制范围和衡量结果。
- 能通过机制与指导提高他人能力，而非形成个人依赖。
- 能在商业目标、用户权益和工程责任间保持职业判断。

###### A.4.1.1.1 通过证据

一次跨团队项目的调研、试点与推广材料；一个成员培养案例；一次设计评审主持记录；一份带量化结果的技术路线图；来自产品、后端、测试和管理者的多角色反馈。

## 附录 B：学习路线使用说明

### B.1 如何裁剪本大纲

#### B.1.1 必修与选修

##### B.1.1.1 裁剪原则

HTML、CSS、JavaScript、TypeScript、浏览器、网络、框架、工程化、测试、性能、安全、监控、架构决策和协作属于主干必修。WebGL、音视频、深度跨端、复杂可视化属于方向选修。Node.js 至少达到能理解 BFF 与服务运行的程度，再根据岗位决定深度。

###### B.1.1.1.1 注意事项

裁剪意味着调整深度和顺序，不意味着永久跳过基础。已有后端经验者可压缩编程通识，但不能跳过浏览器与 CSS；设计转前端者可压缩视觉基础，但必须加强编程、网络和工程化；已有前端经验者应先做能力诊断，直接补证据薄弱的阶段。

### B.2 如何判断可以进入下一阶段

#### B.2.1 四级掌握标准

##### B.2.1.1 理解、实现、应用、指导

- 理解：能准确解释概念、用途、边界和常见误区。
- 实现：能脱离教程完成最小实现并处理典型错误。
- 应用：能在真实约束下选用、测试、监控并维护。
- 指导：能评审他人方案、建立规范并处理演进问题。

###### B.2.1.1.1 阶段通关规则

初级主题至少达到“实现”，岗位核心主题至少达到“应用”，架构师负责的跨团队核心领域应达到“指导”。某个知识点如果只能复述定义但不能通过项目证据证明，就不应在能力评估中标记为掌握。

### B.3 最后提醒

#### B.3.1 路线不是直线

##### B.3.1.1 允许迭代

真实成长会反复回到基础：做性能时重新理解浏览器，做组件库时重新学习 HTML 和可访问性，做微前端时重新审视模块边界，带团队时重新思考代码可读性。回到基础不是退步，而是带着更复杂问题获得更深理解。

###### B.3.1.1.1 终身毕业条件

不存在“学完所有前端技术”的一天。成为前端架构师的标志，是能够持续识别真正问题，选择与约束匹配的方案，带领团队可靠交付，并让系统在需求、技术和人员变化中仍然可理解、可维护、可演进。
