### 模块 01 · CSS 语法、值与单位

<a id="node-02-02-01-01"></a>

#### 规则、声明和错误处理

<a id="node-02-02-01-01-01"></a>

**主题｜CSS 基础语法**

<a id="node-02-02-01-01-01-01"></a>

> **规则结构**

1. <a id="node-02-02-01-01-01-01-01"></a>**样式规则**
   - <a id="node-02-02-01-01-01-01-01-01"></a>**选择器和声明块** — 理解选择目标、属性、值、分号和花括号的语法边界。
     <details id="case-node-02-02-01-01-01-01-01-01" data-knowledge="node-02-02-01-01-01-01-01-01">
     <summary><strong>原子案例｜选择器和声明块</strong></summary>
     
     - **业务切片**：新人把 color 写到选择器花括号外，随后增加更多选择器仍不生效。
     - **失败起点**：没有先区分规则、选择器、声明、属性和值的语法边界。
     - **修正与验证**：用一个按钮规则逐字符标注结构，在开发者工具查看解析结果；分别删除冒号、分号和右括号观察故障隔离。
     
     </details>
   - <a id="node-02-02-01-01-01-01-01-02"></a>**注释与空白** — 掌握 CSS 注释，认识格式空白通常不改变语义但影响可读性。
     <details id="case-node-02-02-01-01-01-01-01-02" data-knowledge="node-02-02-01-01-01-01-01-02">
     <summary><strong>原子案例｜注释与空白</strong></summary>
     
     - **业务切片**：压缩后的 CSS 因错误的双斜线注释吞掉后续声明。
     - **失败起点**：把 JavaScript 注释语法带入 CSS，并认为空白完全不影响维护。
     - **修正与验证**：只使用 CSS 块注释，经过格式化和压缩各跑一次；检查注释边界、字符串和 calc 运算符附近的空白。
     
     </details>
2. <a id="node-02-02-01-01-01-01-02"></a>**容错机制**
   - <a id="node-02-02-01-01-01-01-02-01"></a>**无效声明** — 浏览器忽略不认识的属性或值，其他合法声明仍可生效。
     <details id="case-node-02-02-01-01-01-01-02-01" data-knowledge="node-02-02-01-01-01-01-02-01">
     <summary><strong>原子案例｜无效声明</strong></summary>
     
     - **业务切片**：卡片同时声明未知属性和合法背景色，团队以为整条规则都会失败。
     - **失败起点**：不了解浏览器按声明容错，错误定位范围过大。
     - **修正与验证**：在同一规则放入无效属性、无效值和合法声明，观察 Styles 面板划线；确认合法声明继续生效并编写回退。
     
     </details>
   - <a id="node-02-02-01-01-01-01-02-02"></a>**渐进增强** — 先写广泛支持的回退，再写现代能力；利用容错而不是依赖浏览器猜测错误语法。
     <details id="case-node-02-02-01-01-01-01-02-02" data-knowledge="node-02-02-01-01-01-01-02-02">
     <summary><strong>原子案例｜渐进增强</strong></summary>
     
     - **业务切片**：新版颜色语法写在回退前面，旧语法随后覆盖，现代浏览器也只能看到旧效果。
     - **失败起点**：虽然提供回退，却忽略同一优先级下后声明获胜。
     - **修正与验证**：先写广泛支持值，再写现代值；在支持和不支持环境比较计算值，确保能力增强只覆盖回退。
     
     </details>

<a id="node-02-02-01-01-01-02"></a>

> **at-rule**

1. <a id="node-02-02-01-01-01-02-01"></a>**常用规则**
   - <a id="node-02-02-01-01-01-02-01-01"></a>**`@import`、`@font-face`、`@keyframes`** — 理解各自作用及导入对加载链的潜在影响。
     <details id="case-node-02-02-01-01-01-02-01-01" data-knowledge="node-02-02-01-01-01-02-01-01">
     <summary><strong>原子案例｜`@import`、`@font-face`、`@keyframes`</strong></summary>
     
     - **业务切片**：首页用 @import 串联五层样式，字体和动画直到链末才被发现。
     - **失败起点**：只按文件组织方便选择 at-rule，没有测量加载发现时机。
     - **修正与验证**：将关键样式直接 link，审查 @font-face 字体策略与 @keyframes 命名；用网络瀑布比较多层导入和并行发现。
     
     </details>
   - <a id="node-02-02-01-01-01-02-01-02"></a>**`@media`、`@supports`、`@container`** — 根据环境、能力和容器条件组织样式。
     <details id="case-node-02-02-01-01-01-02-01-02" data-knowledge="node-02-02-01-01-01-02-01-02">
     <summary><strong>原子案例｜`@media`、`@supports`、`@container`</strong></summary>
     
     - **业务切片**：商品卡根据页面宽度写 @media，嵌入窄侧栏后布局错误；又用 @supports 判断设备尺寸。
     - **失败起点**：混淆环境条件、能力条件与容器条件。
     - **修正与验证**：视口和输入环境用 media，语法能力用 supports，局部可用空间用 container；同一组件在三种宿主中验证。
     
     </details>
2. <a id="node-02-02-01-01-01-02-02"></a>**组织规则**
   - <a id="node-02-02-01-01-01-02-02-01"></a>**`@layer`** — 显式管理样式来源层，降低优先级竞赛。
     <details id="case-node-02-02-01-01-01-02-02-01" data-knowledge="node-02-02-01-01-01-02-02-01">
     <summary><strong>原子案例｜`@layer`</strong></summary>
     
     - **业务切片**：第三方组件用高优先级选择器，业务代码不断添加 ID 和 important。
     - **失败起点**：没有先管理来源层，冲突被迫进入优先级军备竞赛。
     - **修正与验证**：声明 reset、base、components、utilities、overrides 的层顺序，把第三方代码放入明确层；用简单类完成覆盖。
     
     </details>
   - <a id="node-02-02-01-01-01-02-02-02"></a>**`@scope` 概念** — 理解局部作用范围和接近度，使用前核对目标浏览器支持。
     <details id="case-node-02-02-01-01-01-02-02-02" data-knowledge="node-02-02-01-01-01-02-02-02">
     <summary><strong>原子案例｜`@scope` 概念</strong></summary>
     
     - **业务切片**：两个嵌套组件都定义 .title，深层标题被外部规则污染。
     - **失败起点**：只靠全局选择器，或在未检查兼容性时直接押注 @scope。
     - **修正与验证**：先用稳定作用域类提供基线，再以 @supports 渐进使用 scope；验证作用域根、边界和接近度。
     
     </details>

<a id="node-02-02-01-02"></a>

#### 值、函数与单位

<a id="node-02-02-01-02-01"></a>

**主题｜数值和尺寸**

<a id="node-02-02-01-02-01-01"></a>

> **绝对与相对单位**

1. <a id="node-02-02-01-02-01-01-01"></a>**常见长度**
   - <a id="node-02-02-01-02-01-01-01-01"></a>**px** — 理解 CSS 像素是参考像素，不等同于设备物理像素。
     <details id="case-node-02-02-01-02-01-01-01-01" data-knowledge="node-02-02-01-02-01-01-01-01">
     <summary><strong>原子案例｜px</strong></summary>
     
     - **业务切片**：设计稿 1px 分隔线在不同 DPR 屏幕上占用的物理像素不同。
     - **失败起点**：把 CSS px 当作固定硬件像素，并据此推算设备清晰度。
     - **修正与验证**：记录 CSS 宽度、devicePixelRatio 和截图物理像素；布局用参考像素，发丝线按实际设备和缩放测试。
     
     </details>
   - <a id="node-02-02-01-02-01-01-01-02"></a>**em 与 rem** — 区分相对当前元素字体和根字体，控制组件缩放与全局缩放。
     <details id="case-node-02-02-01-02-01-01-01-02" data-knowledge="node-02-02-01-02-01-01-01-02">
     <summary><strong>原子案例｜em 与 rem</strong></summary>
     
     - **业务切片**：卡片内层用 em 叠加两次后间距意外放大，用户调整根字号时部分区域又不缩放。
     - **失败起点**：没有区分相对当前字号与根字号的传递方式。
     - **修正与验证**：全局排版和可访问缩放使用 rem，确需随组件字级变化的局部尺寸使用 em；嵌套三层并调整根字号验证。
     
     </details>
2. <a id="node-02-02-01-02-01-01-02"></a>**百分比与视口**
   - <a id="node-02-02-01-02-01-01-02-01"></a>**`%`** — 理解不同属性的百分比参考对象可能不同。
     <details id="case-node-02-02-01-02-01-01-02-01" data-knowledge="node-02-02-01-02-01-01-02-01">
     <summary><strong>原子案例｜`%`</strong></summary>
     
     - **业务切片**：元素 width:50% 和 margin-top:10% 的参考尺寸不同于团队直觉。
     - **失败起点**：把所有百分比都理解为“父元素对应方向的一半”。
     - **修正与验证**：对宽度、内边距、变换和定位分别建立最小实验，查看包含块与参考轴；改变父容器宽高记录计算结果。
     
     </details>
   - <a id="node-02-02-01-02-01-01-02-02"></a>**vw、vh 与动态视口单位** — 处理移动浏览器工具栏变化，认识 svh、lvh、dvh。
     <details id="case-node-02-02-01-02-01-01-02-02" data-knowledge="node-02-02-01-02-01-01-02-02">
     <summary><strong>原子案例｜vw、vh 与动态视口单位</strong></summary>
     
     - **业务切片**：移动页使用 100vh，地址栏和键盘变化时底部按钮被遮挡。
     - **失败起点**：只使用传统视口高度，没有区分小、大和动态视口。
     - **修正与验证**：比较 vh、svh、lvh、dvh 在工具栏展开、收起、横屏和软键盘下的值，为任务选择稳定或动态策略。
     
     </details>
3. <a id="node-02-02-01-02-01-01-03"></a>**容器和字体相关单位**
   - <a id="node-02-02-01-02-01-01-03-01"></a>**cqi 等容器单位** — 让局部组件尺寸随查询容器变化。
     <details id="case-node-02-02-01-02-01-01-03-01" data-knowledge="node-02-02-01-02-01-01-03-01">
     <summary><strong>原子案例｜cqi 等容器单位</strong></summary>
     
     - **业务切片**：嵌入仪表盘侧栏的图表标题仍按整个窗口 vw 放大，文字溢出组件。
     - **失败起点**：组件尺寸依赖全局视口，没有跟随自身容器。
     - **修正与验证**：建立查询容器，用 cqi 控制局部流式尺寸并设置上下界；在宽页面窄栏和独立宽卡中验证。
     
     </details>
   - <a id="node-02-02-01-02-01-01-03-02"></a>**ch、ex、lh** — 在文本宽度、排版基线和行高节奏中谨慎使用。
     <details id="case-node-02-02-01-02-01-01-03-02" data-knowledge="node-02-02-01-02-01-01-03-02">
     <summary><strong>原子案例｜ch、ex、lh</strong></summary>
     
     - **业务切片**：正文 max-width:65ch 在中文和代码片段中产生完全不同的阅读宽度。
     - **失败起点**：把 ch、ex、lh 当作跨字体、跨语言的绝对排版常量。
     - **修正与验证**：分别用中文、英文、等宽代码和回退字体测量，按内容校准行长；用 lh 建节奏时检查字体和用户行高变化。
     
     </details>

<a id="node-02-02-01-02-01-02"></a>

> **计算函数**

1. <a id="node-02-02-01-02-01-02-01"></a>**`calc()`**
   - <a id="node-02-02-01-02-01-02-01-01"></a>**混合单位** — 组合百分比、长度和变量，保留运算符必要空白。
     <details id="case-node-02-02-01-02-01-02-01-01" data-knowledge="node-02-02-01-02-01-02-01-01">
     <summary><strong>原子案例｜混合单位</strong></summary>
     
     - **业务切片**：侧栏宽度写 calc(100%-2rem) 后整条声明无效。
     - **失败起点**：忽略加减运算符必要空白，或没有确认混合单位参与的参考对象。
     - **修正与验证**：修正为有空白的运算式，在开发者工具查看 computed value；改变容器、根字号和变量验证公式含义。
     
     </details>
   - <a id="node-02-02-01-02-01-02-01-02"></a>**使用边界** — 先考虑布局系统能否自然表达，不用复杂公式掩盖错误结构。
     <details id="case-node-02-02-01-02-01-02-01-02" data-knowledge="node-02-02-01-02-01-02-01-02">
     <summary><strong>原子案例｜使用边界</strong></summary>
     
     - **业务切片**：布局用七层 calc 抵消错误 DOM 结构，任何文案变化都会破裂。
     - **失败起点**：把公式复杂度当作工程能力，没有先判断 Flex、Grid 或正常流能否表达。
     - **修正与验证**：先写出内容约束和布局关系，能由布局系统解决就删除公式；只有真实混合单位需求保留并补边界测试。
     
     </details>
2. <a id="node-02-02-01-02-01-02-02"></a>**范围函数**
   - <a id="node-02-02-01-02-01-02-02-01"></a>**min、max** — 在可用空间和内容约束之间选择结果。
     <details id="case-node-02-02-01-02-01-02-02-01" data-knowledge="node-02-02-01-02-01-02-02-01">
     <summary><strong>原子案例｜min、max</strong></summary>
     
     - **业务切片**：搜索栏希望至少 16rem、最多 32rem、同时不超过可用空间，却用多条媒体查询硬切。
     - **失败起点**：没有利用 min、max 直接表达上下约束。
     - **修正与验证**：用 min 或 max 组合可用空间与上限，在 200% 缩放和极窄容器检查结果；说明函数选取较小或较大值的原因。
     
     </details>
   - <a id="node-02-02-01-02-01-02-02-02"></a>**clamp** — 建立流式字号、间距和尺寸的上下界。
     <details id="case-node-02-02-01-02-01-02-02-02" data-knowledge="node-02-02-01-02-01-02-02-02">
     <summary><strong>原子案例｜clamp</strong></summary>
     
     - **业务切片**：标题字号只写 4vw，超宽屏巨大、小屏又不可读。
     - **失败起点**：流式值没有最小和最大保护。
     - **修正与验证**：用 clamp 建立可读下界、随宽度变化的首选值和设计上界；测试 320px、宽屏、缩放和长标题换行。
     
     </details>

<a id="node-02-02-01-02-02"></a>

**主题｜颜色、图片与自定义属性**

<a id="node-02-02-01-02-02-01"></a>

> **颜色值**

1. <a id="node-02-02-01-02-02-01-01"></a>**颜色表示**
   - <a id="node-02-02-01-02-02-01-01-01"></a>**关键字、HEX、RGB、HSL** — 理解透明通道和常用格式互换。
     <details id="case-node-02-02-01-02-02-01-01-01" data-knowledge="node-02-02-01-02-02-01-01-01">
     <summary><strong>原子案例｜关键字、HEX、RGB、HSL</strong></summary>
     
     - **业务切片**：主题色在 HEX、RGB、HSL 间复制时透明度丢失，设计与实现对不上。
     - **失败起点**：只记颜色字符串，没有区分通道、透明度和等价转换。
     - **修正与验证**：选择一个品牌色用多种格式表达并比较计算值；叠加在不同背景上验证透明通道而非只看色板。
     
     </details>
   - <a id="node-02-02-01-02-02-01-01-02"></a>**现代色彩空间** — 认识 Lab、LCH、OKLCH 和广色域，提供兼容回退并控制输出设备差异。
     <details id="case-node-02-02-01-02-02-01-01-02" data-knowledge="node-02-02-01-02-02-01-01-02">
     <summary><strong>原子案例｜现代色彩空间</strong></summary>
     
     - **业务切片**：设计令牌改用 OKLCH 后，旧浏览器整条颜色声明失效，广色域屏又过饱和。
     - **失败起点**：只追求现代色彩空间，没有回退和色域映射策略。
     - **修正与验证**：先提供 sRGB 回退，再提供 OKLCH 或广色域值；在能力检测、普通屏、广色域屏和打印输出中比较。
     
     </details>
2. <a id="node-02-02-01-02-02-01-02"></a>**特殊颜色**
   - <a id="node-02-02-01-02-02-01-02-01"></a>**transparent 与 currentColor** — 利用当前文字色统一图标、边框和装饰。
     <details id="case-node-02-02-01-02-02-01-02-01" data-knowledge="node-02-02-01-02-02-01-02-01">
     <summary><strong>原子案例｜transparent 与 currentColor</strong></summary>
     
     - **业务切片**：图标边框分别写死三种颜色，按钮主题变化后图标仍是旧色。
     - **失败起点**：没有利用 currentColor 继承当前文本色；透明色又被误认为不存在的颜色。
     - **修正与验证**：让图标、边框和装饰使用 currentColor，通过容器 color 统一状态；在透明背景叠加和禁用态验证。
     
     </details>
   - <a id="node-02-02-01-02-02-01-02-02"></a>**系统颜色** — 了解高对比度和强制颜色模式下系统颜色的意义。
     <details id="case-node-02-02-01-02-02-01-02-02" data-knowledge="node-02-02-01-02-02-01-02-02">
     <summary><strong>原子案例｜系统颜色</strong></summary>
     
     - **业务切片**：高对比度模式下自定义背景被系统替换，按钮文字与边框消失。
     - **失败起点**：仍依赖品牌色值，没有理解系统颜色会跟随用户方案。
     - **修正与验证**：在 forced-colors 环境使用合适系统颜色并保留结构边界；检查普通、选中、禁用和焦点状态。
     
     </details>

     - **修正与验证**：在不同作用域覆盖变量，查看继承与使用时计算；为关键令牌建立类型约束或自动化可视测试。

     - **失败起点**：以为 var 回退可以修复任何下游属性错误。
     - **修正与验证**：分别测试未定义、循环引用和定义但在属性中无效的变量，设计多级回退并检查最终 computed value。

     - **失败起点**：原始色值令牌承担了多种业务用途。

   - <a id="node-02-02-02-01-02-01-01-01"></a>**hover、active、focus** — 区分指针悬停、激活和焦点，不让 hover 成为访问内容的唯一方式。

#### 层叠算法

<a id="node-02-02-02-02-01"></a>

**主题｜来源、层和优先级**

<a id="node-02-02-02-02-01-01"></a>

> **决胜顺序**

1. <a id="node-02-02-02-02-01-01-01"></a>**层叠来源和重要性**
   - <a id="node-02-02-02-02-01-01-01-01"></a>**用户代理、用户、作者** — 理解浏览器默认、用户偏好和作者样式来源。
     <details id="case-node-02-02-02-02-01-01-01-01" data-knowledge="node-02-02-02-02-01-01-01-01">
     <summary><strong>原子案例｜用户代理、用户、作者</strong></summary>
     
     - **业务切片**：用户样式要求大字体，却被作者样式层层覆盖；开发者又忘记浏览器默认 margin 来源。
     - **失败起点**：只从项目 CSS 解释结果，没有考虑用户代理、用户和作者来源。
     - **修正与验证**：在 Styles 面板标记每个来源，添加用户偏好实验；重置默认样式时逐项决定而不是全局盲清。
     
     </details>
   - <a id="node-02-02-02-02-01-01-01-02"></a>**normal 与 important** — 知道重要声明会改变来源优先顺序，不用它掩盖结构问题。
     <details id="case-node-02-02-02-02-01-01-01-02" data-knowledge="node-02-02-02-02-01-01-01-02">
     <summary><strong>原子案例｜normal 与 important</strong></summary>
     
     - **业务切片**：组件库到处使用 !important，业务方只能叠加更复杂 important。
     - **失败起点**：把 important 当作“最强声明”，忽略它会改变来源顺序并增加用户覆盖风险。
     - **修正与验证**：先定位冲突维度，普通组件移除 important；只有受控工具类等明确例外保留并记录，验证用户重要样式。
     
     </details>
2. <a id="node-02-02-02-02-01-01-02"></a>**层叠层和作用范围**
   - <a id="node-02-02-02-02-01-01-02-01"></a>**layer 顺序** — 为 reset、基础、组件、工具和覆盖建立显式次序。
     <details id="case-node-02-02-02-02-01-01-02-01" data-knowledge="node-02-02-02-02-01-01-02-01">
     <summary><strong>原子案例｜layer 顺序</strong></summary>
     
     - **业务切片**：团队把 overrides 层声明在 components 之前，简单覆盖规则始终失败。
     - **失败起点**：只知道有 @layer，没有理解层的声明次序决定普通声明优先级。
     - **修正与验证**：在入口先固定层顺序，再分文件填充；调换文件加载顺序仍应稳定，并单独检查 important 的层顺序反转。
     
     </details>
   - <a id="node-02-02-02-02-01-01-02-02"></a>**scoped proximity** — 了解作用域接近度在支持环境中的比较位置。
     <details id="case-node-02-02-02-02-01-01-02-02" data-knowledge="node-02-02-02-02-01-01-02-02">
     <summary><strong>原子案例｜scoped proximity</strong></summary>
     
     - **业务切片**：两个 scope 中同优先级规则都命中按钮，团队只比较源码先后。
     - **失败起点**：忽略作用域接近度在层叠维度中的位置。
     - **修正与验证**：建立嵌套作用域实验，记录作用域根到元素的跳数；支持环境验证接近规则胜出，不支持时基线仍正确。
     
     </details>
3. <a id="node-02-02-02-02-01-01-03"></a>**优先级和源码顺序**
   - <a id="node-02-02-02-02-01-01-03-01"></a>**specificity** — 计算 ID、类属性伪类、类型伪元素三组权重，理解内联声明的位置。
     <details id="case-node-02-02-02-02-01-01-03-01" data-knowledge="node-02-02-02-02-01-01-03-01">
     <summary><strong>原子案例｜specificity</strong></summary>
     
     - **业务切片**：#checkout .card button 看似只有一个 ID，实际权重远高于 .card__action.is-danger。
     - **失败起点**：凭选择器长度猜优先级，无法解释覆盖结果。
     - **修正与验证**：把 ID、类属性伪类、类型伪元素分别计数，加入内联声明对照；在 DevTools 查看被覆盖原因并手算复核。
     
     </details>
   - <a id="node-02-02-02-02-01-01-03-02"></a>**order of appearance** — 所有更高维度相等时，后出现声明获胜。
     <details id="case-node-02-02-02-02-01-01-03-02" data-knowledge="node-02-02-02-02-01-01-03-02">
     <summary><strong>原子案例｜order of appearance</strong></summary>
     
     - **业务切片**：两条声明来源、层和优先级完全相同，但团队认为“离元素更近的文件”会赢。
     - **失败起点**：在所有更高维度相等后，没有回到源码出现顺序。
     - **修正与验证**：创建相同选择器的两条规则，改变导入与打包顺序；确认后出现者获胜，并用固定入口顺序消除偶然性。
     
     </details>

<a id="node-02-02-02-02-01-02"></a>

> **优先级控制**

1. <a id="node-02-02-02-02-01-02-01"></a>**低权重策略**
   - <a id="node-02-02-02-02-01-02-01-01"></a>**单类组件** — 让调用方无需复制内部结构即可覆盖合理样式。
     <details id="case-node-02-02-02-02-01-02-01-01" data-knowledge="node-02-02-02-02-01-02-01-01">
     <summary><strong>原子案例｜单类组件</strong></summary>
     
     - **业务切片**：调用方为了改按钮颜色必须复制组件内部四层 DOM 选择器。
     - **失败起点**：组件没有稳定、低成本的覆盖接口。
     - **修正与验证**：组件主体使用单类和语义变量，公开状态类或属性；在不知道内部标签结构的情况下完成主题覆盖。
     
     </details>
   - <a id="node-02-02-02-02-01-02-01-02"></a>**`:where()`** — 为基础或容器规则提供零优先级包装。
     <details id="case-node-02-02-02-02-01-02-01-02" data-knowledge="node-02-02-02-02-01-02-01-02">
     <summary><strong>原子案例｜`:where()`</strong></summary>
     
     - **业务切片**：全局基础规则 .prose h2 优先级过高，文章内嵌组件标题被污染。
     - **失败起点**：基础样式不该竞争却携带普通选择器权重。
     - **修正与验证**：用 :where(.prose) :where(h2) 或边界类建立零/低优先级基线，让组件单类自然覆盖，并做嵌套测试。
     
     </details>
2. <a id="node-02-02-02-02-01-02-02"></a>**反模式**
   - <a id="node-02-02-02-02-01-02-02-01"></a>**选择器军备竞赛** — 不通过不断增加父级和 ID 解决覆盖问题。
     <details id="case-node-02-02-02-02-01-02-02-01" data-knowledge="node-02-02-02-02-01-02-02-01">
     <summary><strong>原子案例｜选择器军备竞赛</strong></summary>
     
     - **业务切片**：修一个按钮颜色时，从 .button 增长到 body #app main .dialog .button。
     - **失败起点**：用更长选择器赢一次冲突，没有查明来源层和组件边界。
     - **修正与验证**：在层叠面板按来源、层、重要性、优先级、顺序依次定位；回到合适层或接口修复并删除升级链。
     
     </details>
   - <a id="node-02-02-02-02-01-02-02-02"></a>**important 滥用** — 仅在受控工具类或必须压过不可控来源等明确场景使用并记录原因。
     <details id="case-node-02-02-02-02-01-02-02-02" data-knowledge="node-02-02-02-02-01-02-02-02">
     <summary><strong>原子案例｜important 滥用</strong></summary>
     
     - **业务切片**：为了确保隐藏工具类有效，项目所有工具类都加 !important，动画和可访问状态无法恢复。
     - **失败起点**：没有限定 important 工具类的职责和撤销路径。
     - **修正与验证**：只在明确原子工具层、需要压过组件且有文档时使用；提供反向工具或更高层策略，并测试用户样式。
     
     </details>

<a id="node-02-02-02-02-02"></a>

**主题｜继承、初始值和计算值**

<a id="node-02-02-02-02-02-01"></a>

> **属性值生命周期**

1. <a id="node-02-02-02-02-02-01-01"></a>**声明到使用**
   - <a id="node-02-02-02-02-02-01-01-01"></a>**specified、computed** — 理解层叠后指定值如何解析为计算值。
     <details id="case-node-02-02-02-02-02-01-01-01" data-knowledge="node-02-02-02-02-02-01-01-01">
     <summary><strong>原子案例｜specified、computed</strong></summary>
     
     - **业务切片**：元素声明 width:var(--size)，变量来自 em；团队把源码字符串当作最终宽度。
     - **失败起点**：没有区分层叠选出的指定值与解析继承后的计算值。
     - **修正与验证**：在 DevTools 同时记录 specified 和 computed，改变父级字号与变量作用域；解释何时相对值被解析。
     
     </details>
   - <a id="node-02-02-02-02-02-01-01-02"></a>**used、actual** — 理解布局和设备取整后最终使用值可能变化。
     <details id="case-node-02-02-02-02-02-01-01-02" data-knowledge="node-02-02-02-02-02-01-01-02">
     <summary><strong>原子案例｜used、actual</strong></summary>
     
     - **业务切片**：网格轨道计算为 100.333px，截图实际边缘落在不同设备像素。
     - **失败起点**：把计算值当作设备最终绘制值，忽略布局约束和取整。
     - **修正与验证**：比较 computed、used 和实际像素，改变容器宽度与 DPR；视觉回归容许合理取整而非要求字符串完全相等。
     
     </details>
2. <a id="node-02-02-02-02-02-01-02"></a>**全局关键字**
   - <a id="node-02-02-02-02-02-01-02-01"></a>**initial、inherit、unset** — 显式选择初始值、父级值或按属性继承性处理。
     <details id="case-node-02-02-02-02-02-01-02-01" data-knowledge="node-02-02-02-02-02-01-02-01">
     <summary><strong>原子案例｜initial、inherit、unset</strong></summary>
     
     - **业务切片**：组件希望清除父级 color，却误用 initial；另一个非继承属性误用 inherit 导致布局扩散。
     - **失败起点**：没有按属性继承性理解 initial、inherit、unset。
     - **修正与验证**：对继承属性和非继承属性各建一组对照，观察三关键字结果；在组件重置中明确想要浏览器初始还是父值。
     
     </details>
   - <a id="node-02-02-02-02-02-01-02-02"></a>**revert、revert-layer** — 回退到较早来源或层，适用于撤销组件或第三方覆盖。
     <details id="case-node-02-02-02-02-02-01-02-02" data-knowledge="node-02-02-02-02-02-01-02-02">
     <summary><strong>原子案例｜revert、revert-layer</strong></summary>
     
     - **业务切片**：第三方卡片主题需要撤销当前层覆盖，团队手工复制旧值且随主题更新失效。
     - **失败起点**：把回退写成具体值，没有利用来源或层级撤销。
     - **修正与验证**：用 revert 回到较早来源，用 revert-layer 撤销当前层；在浏览器默认、基础层、主题层和组件层逐级验证。
     
     </details>

<a id="node-02-02-02-02-02-02"></a>

> **继承边界**

1. <a id="node-02-02-02-02-02-02-01"></a>**默认继承**
   - <a id="node-02-02-02-02-02-02-01-01"></a>**文本相关属性** — 颜色、字体等通常继承，利用容器设置减少重复。
     <details id="case-node-02-02-02-02-02-02-01-01" data-knowledge="node-02-02-02-02-02-02-01-01">
     <summary><strong>原子案例｜文本相关属性</strong></summary>
     
     - **业务切片**：文章容器设置 color 和 font 后，内部每个 span 仍重复相同声明。
     - **失败起点**：没有利用文本属性的自然继承，规则数量和覆盖面膨胀。
     - **修正与验证**：在语义容器设置字体与颜色，只在真实差异处覆盖；通过 computed 面板追踪继承来源并测试嵌套链接。
     
     </details>
   - <a id="node-02-02-02-02-02-02-01-02"></a>**盒模型属性** — 尺寸、边距、边框通常不继承，避免误判子元素布局来源。
     <details id="case-node-02-02-02-02-02-02-01-02" data-knowledge="node-02-02-02-02-02-02-01-02">
     <summary><strong>原子案例｜盒模型属性</strong></summary>
     
     - **业务切片**：开发者以为 border 和 margin 会从卡片继承到按钮，给父元素加值却无效。
     - **失败起点**：把所有 CSS 属性都套用文本继承经验。
     - **修正与验证**：选取颜色、字体、边距、边框、宽度做继承矩阵；在子元素 computed 面板确认盒模型属性需要显式规则。
     
     </details>
2. <a id="node-02-02-02-02-02-02-02"></a>**表单控件**
   - <a id="node-02-02-02-02-02-02-02-01"></a>**字体继承差异** — 通过明确规则使按钮和输入继承应用字体。
     <details id="case-node-02-02-02-02-02-02-02-01" data-knowledge="node-02-02-02-02-02-02-02-01">
     <summary><strong>原子案例｜字体继承差异</strong></summary>
     
     - **业务切片**：页面使用品牌字体，但 input 和 button 仍显示系统字体。
     - **失败起点**：假设所有原生表单控件都会继承字体。
     - **修正与验证**：对按钮、输入、选择框明确设置 font:inherit 或设计令牌；测试禁用、自动填充和不同系统控件。
     
     </details>
   - <a id="node-02-02-02-02-02-02-02-02"></a>**原生外观** — 认识不同系统控件的默认样式和 `appearance` 的代价。
     <details id="case-node-02-02-02-02-02-02-02-02" data-knowledge="node-02-02-02-02-02-02-02-02">
     <summary><strong>原子案例｜原生外观</strong></summary>
     
     - **业务切片**：为统一 select 和 checkbox，团队直接 appearance:none，却没有重建箭头、焦点和禁用状态。
     - **失败起点**：只移除原生外观，没有承担被移除的可用性责任。
     - **修正与验证**：先决定是否真需重绘；若移除 appearance，完整实现状态、命中区、强制颜色和多浏览器回退。
     
     </details>

<a id="case-c06"></a>

#### 案例驱动｜C06：层叠冲突侦探实验室

**业务背景**

团队接手一个活动报名页。组件库按钮应该是蓝色，活动主题把它改成紫色，危险按钮应该是红色，禁用按钮应该是灰色。实际页面中，有的危险按钮仍为紫色，有的禁用按钮保持红色，开发者通过添加三个 `!important` 暂时修复，结果暗色主题再次失效。

**关联知识点**

- [选择器体系](#node-02-02-02-01)
- [层叠来源、层与优先级](#node-02-02-02-02-01)
- [继承与计算值](#node-02-02-02-02-02)
- [自定义属性](#node-02-02-01-02-02-02)
- 系统化调试流程（跨模块延伸）

**现场代码**

```css
button { color: white; background: royalblue; }
.campaign-page .toolbar button { background: rebeccapurple; }
.button--danger { background: crimson; }
button:disabled { background: gray !important; }

[data-theme="dark"] .campaign-page button.button--danger {
  background: color-mix(in srgb, crimson 70%, black);
}
```

页面还有内联样式、第三方表单 CSS 和用户高对比度设置。只计算三个选择器的数字优先级，无法解释全部结果，因为层叠还要比较来源、重要性、层、作用域、优先级和出现顺序。

**案例推进**

> **任务一：建立证据表**

在开发者工具中选择每一种按钮，记录最终 background 的所有候选声明：文件、选择器、是否 important、所属 layer、优先级、是否被划掉。不要先改代码。把每次“为什么输掉”写成一句完整规则。

> **任务二：重新设计层级**

建立明确层叠层：reset、base、components、themes、utilities、overrides。组件按钮不关心具体活动主题，只消费语义变量：

```css
@layer reset, base, components, themes, utilities, overrides;

@layer components {
  .button {
    color: var(--button-fg, CanvasText);
    background: var(--button-bg, ButtonFace);
  }
  .button[data-variant="danger"] {
    --button-bg: var(--color-action-danger);
  }
}

@layer themes {
  [data-campaign="summer"] {
    --color-action-primary: rebeccapurple;
  }
}
```

危险变体、主题和禁用状态不是同一维度。主题改变品牌主操作色，但不能把危险语义改成品牌色。禁用状态应提供清晰不可操作反馈，同时仍满足可读性。

> **任务三：处理继承和变量失效**

故意删除 `--color-action-danger`，观察 var 没有回退时整条声明如何失效。再把一个自定义属性定义为不合法颜色，区分“变量存在”和“属性在使用处有效”。检查 SVG 图标用 currentColor 时如何继承按钮前景色。

> **任务四：允许业务覆盖**

设计调用方允许修改的变量和不允许依赖的内部结构。调用方不应写 `.campaign-page .toolbar > div:nth-child(2) button`。为确有需要的覆盖提供组件变量、数据变体或低权重包装，而不是要求更长选择器。

**故障卡片**

逐一解释并修复：

1. `:where(.form) button` 为什么容易被覆盖？它何时是优点？
2. `:is(#fake-id, .button)` 为什么会意外获得高优先级？
3. 为什么未分层的 normal 样式可能胜过层内 normal 样式？
4. 为什么 layer 顺序对 important 声明的比较方向需要特别谨慎？
5. 为什么 `all: unset` 会让按钮丢失比预想更多的行为和继承？
6. 简写 `background` 为什么会重置已经设置的 background-image？
7. 内联样式应该通过什么契约替代，什么情况下确实需要外部 important？

**验收清单**

- [ ] 不增加选择器长度也能解释并解决四类按钮冲突。
- [ ] 组件、主题、语义状态和工具类拥有清晰层次。
- [ ] 删除令牌、切换主题、插入第三方 CSS 时存在可预测回退。
- [ ] 项目中 important 有明确数量、用途和审查规则。
- [ ] 能从 Computed 面板追溯最终值，不依赖试错添加规则。

**迁移挑战**

不能一次删除旧 CSS。请用一个发布周期完成双轨迁移：先引入 layer 包裹旧样式，再迁移按钮和表单，最后收缩 override。定义每一步的回滚条件和“旧规则可以删除”的证据。
