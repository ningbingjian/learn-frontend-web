## 理论讲解

### 1. 编码与解码不一致

乱码通常不是字符“随机损坏”，而是实际字节采用一种编码，读取方却使用另一种编码。UTF-8 字节被当作 Windows-1252 解码时，就可能出现 `ä¸­æ–‡` 一类文本。

### 2. 区分常见表现

- `�` 通常表示当前解码器遇到无效字节序列。
- 方框或空白字形可能是字体缺少字符，并不一定是编码问题。
- `&amp;#x4E2D;` 一类文本可能是转义层级错误。
- 错误文本再次编码并保存后，问题可能已经进入数据库或缓存。

### 3. 按链路定位第一次错误

诊断顺序应保持稳定：原始字符、实际字节、HTTP 和 HTML 声明、所用解码器、最终字符。重点是找到第一次发生变化的位置，而不是反复尝试不明转码。

## 源码讲解

[`index.html`](./index.html) 先用 `TextEncoder` 把“中文”转换为同一组 UTF-8 字节，再分别交给 UTF-8 和 Windows-1252 解码器。

脚本输出原始字符、十六进制字节、两种解码结果和结论。两次解码使用完全相同的字节，因此差异只能来自解码方式。

## 运行案例

使用浏览器打开 [`index.html`](./index.html)，从上到下核对字符、字节和两种解码结果。将原始字符串改为 `café` 或其他文本，保存并刷新后重新比较。

通过本地服务器运行时，在当前目录执行 `python3 -m http.server 8080`，访问 `http://localhost:8080/index.html`。

## 效果验证

- 原始字符和 UTF-8 解码结果都应为“中文”。
- 两种解码使用的字节都应为 `e4 b8 ad e6 96 87`。
- Windows-1252 解码结果应出现与中文不同的乱码文本。
- 实验应能证明：字节没有变化，第一次错误发生在解码方式。
