## 学习目标

学完本节后，你应该能够：

1. 理解乱码通常来自“字节”和“解码方式”不匹配，而不是字符随机损坏。
2. 区分常见乱码、替换字符 `�`、字体缺字和转义错误。
3. 建立固定的乱码排查链路：原始字符 → 字节 → 声明 → 解码器 → 最终字符。
4. 能通过“同一组字节、两种解码方式”的实验定位第一次错误发生在哪一层。

> **本节核心知识是乱码诊断思路，不是 JavaScript API。**  
> `TextEncoder`、`TextDecoder`、`Array.from()` 等全部属于实验辅助代码。

## 理论讲解

### 1. 乱码通常是“解码错了”

正确链路：

```text
字符
  ↓ 正确编码
字节
  ↓ 正确解码
字符
```

如果字节本身是 UTF-8，但读取方使用其他编码规则：

```text
UTF-8 字节
  ↓ 错误解码器
错误字符
```

就可能出现乱码。

### 2. 常见表现不完全等价

排查时要区分：

- `ä¸­æ–‡` 一类文本：常见于编码/解码不一致。
- `�`：通常表示解码器遇到无法按当前编码解释的字节序列。
- 方框、空白字形：可能是字体缺少对应字符。
- `&amp;#x4E2D;`：可能是转义层级错误。
- 错误字符再次保存：问题可能已经进入数据库、缓存或消息队列。

### 3. 找“第一次变错”的位置

推荐固定按下面顺序排查：

```text
原始字符是什么？
      ↓
实际字节是什么？
      ↓
HTTP / HTML 声明是什么？
      ↓
实际使用什么解码器？
      ↓
最终得到什么字符？
```

不要一看到乱码就反复尝试转码；先找第一次发生变化的位置。

## 动手编码：从 0 到 1 完成案例

### 第 0 步：明确实验设计

我们要控制一个变量：

> 两次解码使用完全相同的一组 UTF-8 字节，只改变解码方式。

如果最终结果不同，就能证明差异来自解码器，而不是字节发生变化。

### 第 1 步：写页面骨架

创建 `index.html`：

```html
<!doctype html>
<html lang="zh-CN">
<head>
  <meta charset="utf-8">
  <title>KP010：乱码诊断</title>
</head>
<body>
  <h1>同一组字节，不同解码结果</h1>
  <pre id="result"></pre>
</body>
</html>
```

这里先保证案例文件本身按 UTF-8 正常运行。

### 第 2 步：确定原始字符

在 `body` 末尾加入：

```html
<script>
  const original = '中文';
</script>
```

### 第 3 步：编码成 UTF-8 字节

继续加入：

```js
const bytes = new TextEncoder().encode(original);
```

> `TextEncoder` 是实验辅助代码，只用于获得可控的 UTF-8 字节。

当前链路：

```text
中文
  ↓ UTF-8 编码
bytes
```

### 第 4 步：用正确的 UTF-8 解码

继续加入：

```js
const correct =
  new TextDecoder('utf-8').decode(bytes);
```

预期：

```text
原始字符：中文
UTF-8 解码：中文
```

这证明这组字节本身能够正确还原原文。

### 第 5 步：对同一组字节故意使用错误解码器

继续加入：

```js
const wrong =
  new TextDecoder('windows-1252').decode(bytes);
```

最关键的是：

```text
correct 使用 bytes
wrong   也使用 bytes
```

字节没有变化，只有解码方式不同。

### 第 6 步：把字节转成十六进制

继续加入：

```js
const hex = Array.from(
  bytes,
  value => value.toString(16).padStart(2, '0')
).join(' ');
```

这样可以明确看到两次解码共享的字节：

```text
e4 b8 ad e6 96 87
```

### 第 7 步：输出完整诊断链路

最后加入：

```js
document.querySelector('#result').textContent = [
  '原始字符：' + original,
  '实际字节：' + hex,
  'UTF-8 解码：' + correct,
  'Windows-1252 解码：' + wrong,
  '',
  '结论：字节没有变化，错误发生在解码方式。'
].join('\n');
```

刷新后从上往下读：

```text
原始字符
   ↓
实际字节
   ↓
正确解码结果
   ↓
错误解码结果
   ↓
结论
```

### 第 8 步：更换原始文本验证

临时把：

```js
const original = '中文';
```

改成：

```js
const original = 'café';
```

观察：

- 字节发生变化。
- UTF-8 解码仍能正确还原。
- 错误解码器可能产生另一种异常文本。

最后恢复 `'中文'`。

### 第 9 步：把方法迁移到真实问题

以后遇到真实乱码，不要机械照搬 `windows-1252`，而要问：

```text
数据最初是什么字符？
实际落盘/传输的字节是什么？
哪一层声明了什么 charset？
哪一层真正使用了什么解码方式？
第一次变错发生在哪里？
```

### 第 10 步：完成案例并对照最终源码

恢复原始文本后，你的代码应与仓库最终 [`index.html`](./index.html) 一致。

本节总结：

- **核心知识**：固定按“字符 → 字节 → 声明 → 解码器 → 最终字符”追踪，找到第一次错误。
- **实验辅助代码**：`TextEncoder`、`TextDecoder`、十六进制输出，只用于制造一个可控的对照实验。

你应该能够确认：

- 原始字符为“中文”。
- 实际字节为 `e4 b8 ad e6 96 87`。
- UTF-8 解码结果仍然是“中文”。
- Windows-1252 解码结果与原文不同。
