## 学习目标

完成本节后，你应该能够：

1. 判断数据表格在小屏上为什么容易出现横向溢出。
2. 使用滚动容器保留完整列和原生 `<table>` 语义。
3. 使用 `min-width` 保证单元格不被压缩到不可读。
4. 通过列顺序体现关键列优先级，而不是随意删除重要数据。
5. 理解把 `tr`、`td` 改成 `display: block` 或直接重构成 `div` 卡片可能带来的语义风险。
6. 能用 `scrollWidth`、`clientWidth` 和实际窄屏测试验证方案。

## 理论讲解

### 1. 小屏的核心矛盾

桌面数据表格经常有很多列：

```text
套餐 | 月价 | 用户数 | 存储 | API 调用 | SLA | 支持方式
```

如果把这 7 列强行压进 360px 宽的手机屏幕，常见后果包括：

- 列宽过窄。
- 单词和数字被频繁换行。
- 表头与数据难以对应。
- 用户需要不断上下扫视才能理解一行。

所以“响应式表格”并不意味着必须把所有内容压进屏幕宽度。

一个更稳健的目标是：

> 保留数据关系，让用户在需要时横向查看更多列。

### 2. 横向滚动是稳健的基础方案

基础结构仍然是原生表格：

```html
<div class="table-scroll" role="region" aria-labelledby="pricing-title" tabindex="0">
  <table>
    ...
  </table>
</div>
```

CSS 让外层负责滚动：

```css
.table-scroll {
  overflow-x: auto;
}

.table-scroll table {
  min-width: 760px;
}
```

这样做的关键点是：

- `<table>` 仍然是 `<table>`。
- `<th>`、`scope` 等表头关系不需要被拆掉。
- 小屏只改变查看方式，不改变数据模型。

`tabindex="0"` 让滚动区域可以通过键盘获得焦点，便于某些键盘用户在横向溢出时操作；是否加入它应结合真实交互和浏览器行为验证。

### 3. 关键列优先级

小屏上最先看到哪些列，是产品信息架构的一部分。

例如套餐比较表中，通常最重要的列可能是：

1. 套餐名称。
2. 月价。
3. 核心额度。
4. 更次要的 SLA、支持方式。

一种低风险策略是直接在 HTML 中按照重要程度安排列顺序：

```text
套餐 | 月价 | 用户数 | 存储 | API 调用 | SLA | 支持
```

这样用户进入表格后先看到关键决策信息，再横向查看更多细节。

如果业务决定在小屏隐藏次要列，必须明确这是一种“内容取舍”，不是纯技术优化；隐藏后用户真的会失去这些数据，不能把它当作无成本方案。

### 4. 不要为了响应式破坏 table 语义

一些旧式方案会这样处理：

```css
tr,
td {
  display: block;
}
```

或者直接在手机端把表格改写成大量 `<div>`。

这可能带来两个问题：

1. 视觉结构与原始二维关系脱节。
2. 浏览器与辅助技术暴露的表格语义可能变得不可预测或难以理解。

如果产品确实需要“卡片视图”，更稳妥的做法是把它视为另一种信息呈现组件，并重新设计标签、字段名称和可访问关系，而不是简单用 CSS 把表格元素伪装成卡片。

对于一般业务数据表格，优先从下面方案开始：

```text
原生 table
+ 外层横向滚动
+ 合理 min-width
+ 关键列靠前
+ 清晰表头
```

## 动手编码：从 0 到 1

### 第 0 步：创建最小页面

```html
<!doctype html>
<html lang="zh-CN">
<head>
  <meta charset="utf-8">
  <meta name="viewport" content="width=device-width, initial-scale=1">
  <title>KP088 响应式数据表格</title>
</head>
<body>
  <h1 id="pricing-title">SaaS 套餐比较</h1>
</body>
</html>
```

**本步目标**：确保移动设备使用真实设备宽度。

### 第 1 步：先写完整原生表格

```html
<table>
  <thead>
    <tr>
      <th scope="col">套餐</th>
      <th scope="col">月价</th>
      <th scope="col">用户数</th>
      <th scope="col">存储</th>
      <th scope="col">API 调用</th>
      <th scope="col">SLA</th>
      <th scope="col">支持方式</th>
    </tr>
  </thead>
  <tbody>
    ...
  </tbody>
</table>
```

**为什么先不考虑手机**：先把数据关系和表头语义写正确，再处理布局约束。

### 第 2 步：用列顺序体现优先级

把决策最重要的“套餐”“月价”放在最前面。

不要先从“隐藏列”开始，因为隐藏意味着用户无法访问那些数据。

### 第 3 步：增加横向滚动容器

```html
<div
  class="table-scroll"
  role="region"
  aria-labelledby="pricing-title"
  tabindex="0"
>
  <table>...</table>
</div>
```

**本步目标**：当表格宽度超过视口时，让溢出发生在局部容器中，而不是让整个页面横向滚动。

### 第 4 步：给表格设置可读的最小宽度

```css
.table-scroll {
  overflow-x: auto;
}

table {
  min-width: 760px;
}
```

**为什么使用 `min-width`**：让每列保持基本可读宽度。当屏幕不足时滚动，而不是无限压缩单元格。

### 第 5 步：增强关键列可发现性

最终案例让第一列在横向滚动时保持 `position: sticky`。

这属于视觉和交互增强，不改变 HTML 表格语义。

关键列仍然必须在 HTML 中拥有正确的 `<th scope="row">` 或 `<th scope="col">` 关系。

### 第 6 步：加入溢出检测

案例使用：

```js
scrollArea.scrollWidth > scrollArea.clientWidth
```

判断当前窗口是否真的发生横向溢出，并输出：

- 容器可视宽度。
- 内容总宽度。
- 是否需要横向滚动。
- 表头顺序。

这些 JavaScript 都是实验辅助代码。

### 第 7 步：加入滚动提示

页面提供一段持久提示：

```html
<p id="scroll-hint">小屏可横向滚动查看全部列。</p>
```

不要只依赖一个渐变阴影来表达“这里还能滚”，因为视觉提示并不一定对所有用户都可感知。

### 第 8 步：对照最终源码

最终可运行文件：

- [index.html](./index.html)

**本节核心代码**：原生 `table` 结构、表头关系、滚动容器和保证可读性的最小宽度策略。

**实验辅助代码**：边框、sticky 效果、尺寸检测和页面观察输出。

## 效果验证

### 验证 1：桌面宽度

当浏览器足够宽时，观察结果通常应显示：

```text
需要横向滚动：否
```

### 验证 2：模拟 375px 手机

在 DevTools 切换到约 375px 宽度。

预期：

- 页面本身不应产生明显横向溢出。
- 表格区域内部可以横向滚动。
- 表格仍然保持行列结构。
- 第一列保持在左侧，帮助用户知道当前正在比较哪个套餐。

### 验证 3：检查 DOM

缩小窗口后检查元素。

不应因为进入手机宽度而把 `<table>`、`<tr>`、`<th>`、`<td>` 替换成无语义 `<div>`。

### 验证 4：检查关键列顺序

页面输出会列出表头顺序。

确认“套餐”“月价”位于最前面，而不是把最关键的信息放在滚动很远的位置。

### 验证 5：键盘体验

使用 Tab 键进入滚动区域，然后尝试方向键或触控板/键盘滚动方式。

实际可用性会受操作系统和浏览器影响，因此必须在目标环境验证。

### 验证 6：读屏与可访问性

使用 Accessibility 面板或读屏器验证表头仍按原生表格关系暴露。

响应式布局的目标应该是“改变查看方式”，而不是破坏已经建立好的表格语义。
